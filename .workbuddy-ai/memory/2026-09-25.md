## MOBA Demo 阶段二：静态交叉审查（Dry Run）与修复

按用户给的 4 个排查项逐条核对，结论与修复：

1. **委托空指针**：`HealthComponent` 的两处广播均使用 `?.Invoke`（`OnHealthChanged?.Invoke` / `OnDied?.Invoke`），其余组件无自定义事件 → 无问题。
2. **接口实现遗漏**：`EntityBase : ITargetable` 三个成员齐备（`TargetTransform` / `Team` / `IsValidTarget`）；`HealthComponent : IDamageable` 两个成员齐备（`TakeDamage` / `IsDead`）→ 无问题。
3. **死尸鞭尸**：原实现只在 `CanAttack` 里通过 `target.IsValidTarget` 间接校验死亡状态。**已修复**：`TryAttack` 在 `ResolveDamageable(target)` 之后新增显式 `damageable.IsDead` 检查——因为 `ITargetable.IsValidTarget`（EntityBase 提供）与 `IDamageable.IsDead`（HealthComponent 提供）来自不同组件，不能假设永远一致。
4. **组件获取时机**：`RequireComponent` 不能加（会把 NavMeshAgent 强加给塔/基地，见既有决策）。真正发现的隐患是**动态创建场景下的引用失效**：
   - **已修复**：`EntityBase` 抽出 `CacheComponents()`，并在新增的 `Initialize(EntityStatsData)` / `Initialize(stats, team, entityType)` 里重新调用一次，补全"Awake 时组件还没挂齐"的引用；新增 `hasInitialized` 标记防止 Start 二次注入（二次注入会把已受伤单位回满血）。
   - **已修复**：`CombatComponent` / `TargetingComponent` 的 `owner` 改为延迟解析属性 `Owner`，并把"缺 EntityBase"的报错从 Awake 移到首次使用（保留一次性标记，避免误报合法用法）。
   - 说明：`GetComponent` 本身不会因 Awake 顺序而找不到同物体上已存在的组件，所以 Awake 缓存机制本身没错；错的是"组件晚于 EntityBase 挂载"这一种动态创建场景。

## 事故复盘：`MOBA.Debug` 命名空间导致全项目编译失败（已修复）

### 现象
Unity 进入 Safe Mode，Console 报 54 条 `error CS0234: The type or namespace name 'Log'/'LogError'/'LogWarning' does not exist in the namespace 'MOBA.Debug'`。可见的报错位于 `Stage2AutoTester.cs(287/303/317)`、`HealthComponent.cs(120/137/158/179)`、`TargetingComponent.cs(233)` —— **全都是与 Debug 目录毫无关系的文件**。

### 根因
上一轮我为 `Assets/Scripts/Debug/FSMDebugView.cs` 按"命名空间 = MOBA.<目录名>"的约定取了 `namespace MOBA.Debug`，并只在**该文件内部**用 `using UnityDebug = UnityEngine.Debug;` 规避冲突。

但真正的杀伤面是反过来的：C# 名字查找中**外层命名空间的成员优先于 using 导入**。一旦存在命名空间 `MOBA.Debug`，`MOBA` 下**所有**文件里的 `Debug` 都会先解析成这个命名空间（`MOBA.Components` 里找不到 `Debug` → 往外找到 `MOBA.Debug` → 命中），于是 `Debug.Log` 变成 `MOBA.Debug.Log` → CS0234。
实测波及 **14 个文件、67 处调用点**（`EntityAIController` 8、`Stage2AutoTester` 14、`PlayerCommandController` 7、`TargetingComponent` 6、`EntityBase` 6、`CombatComponent` 5、`HealthComponent` 5 …）。

**教训：局部别名只能救一个文件，救不了整个命名空间的污染。这类问题必须消除命名空间本身。**

### 修复
- `Assets/Scripts/Debug/FSMDebugView.cs`：命名空间 `MOBA.Debug` → **`MOBA.Debugging`**；删除 `using UnityDebug = UnityEngine.Debug;`，3 处调用恢复为标准的 `Debug.Log*`；文件头写入"必读"说明，注明该例外的原因与"不要改回 MOBA.Debug"。
- **目录名保持 `Assets/Scripts/Debug/` 不变**（用户明确指定了该路径，且与计划书第 2 节目录结构一致）—— 只改命名空间。
- 全项目复查：`namespace MOBA.Debug` 已彻底清除，无任何文件 `using MOBA.Debug`。

### 防复发
- `check_unity_cs.py` 新增第 5 项检查 **危险命名空间末段**：维护 `DANGEROUS_SEGMENTS` 清单（Debug / Time / Physics / Mathf / Color / Object / Component / Transform / Gizmos / Input / Camera / Material / Animator / GUI / Event / Space / ScriptableObject 等 30 个 UnityEngine 常用类型名），只要某个 `MOBA.<X>` 的段命中即报错并说明 CS0234 后果。

## 阶段四：对局中枢 MinionSpawner / MatchController（14:0x）

### 新增文件
- `Assets/Scripts/Gameplay/MinionSpawner.cs`（`MOBA.Gameplay`）：`spawnData` / `team` / `spawnPoint` / `targetLane`；`StartSpawning()` / `StopSpawning()`；协程 `SpawnLoop` 无限出兵。

### 关键设计决策
1. **波次计时基准 = 上一波首个小兵出生时刻**（`waveInterval - elapsed`），保证"每 N 秒必定开一波"；若用"出完再等 N 秒"，周期会随每波数量漂移，与验收标准"按固定间隔生成"不符。`MinionSpawnData` 的 Tooltip 已与此对齐。
2. **生成注入顺序不可颠倒**：`entity.Initialize(entity.StatsData, team, EntityType.Minion)` → **然后** `ai.InitializeAI(targetLane)`。依据 `EntityAIController.InitializeAI` 的文档契约：状态在 Tick 里读的攻击距离/索敌半径必须已注入，否则状态跳转失准。
3. **`MinionSpawner.OnDisable` 必须调 `StopSpawning()`**：Unity 禁用组件时会自动停协程，但**协程句柄不会自动清空**；不清空则重新启用后 `StartSpawning` 误判"已在出兵"而永久拒绝启动。
4. **`Instantiate` 后必须立刻校验并补注入**，缺 `EntityBase`/`EntityAIController` 的半成品实例直接 `Destroy`，避免留下无法交互的垃圾对象。
5. **波次节奏校验（一次性告警）**：`WaveInterval <= 0` 或 `(WaveCount-1)*SpawnInterval >= WaveInterval` 时警告；同时把两个等待值用 `Mathf.Max(0.02f, ...)` 夹住，防止"间隔填 0"时一帧内把整波刷完。
6. **MatchController 只认第一次基地摧毁**（`isMatchOver`）：两个基地可能同帧相继归零，否则胜负会被后一次覆盖。
7. **对局结束日志不受 `logMatchEvents` 开关控制**（每局仅一条、无刷屏风险，且是任务明确要求的结果输出）；开局准备/启动日志受开关控制。

### 已审查的闭环链路（静态层面）
`OnEnable` 订阅 → `Start` 延迟 → `StartSpawning` → `Instantiate` + 双注入 → 小兵推进交战 → 基地 `OnDied` → `BaseCoreController` 广播静态事件 → `MatchController` 停全部 Spawner + 输出获胜方。

计划书阶段四验收还有「停止战斗逻辑」一句：本类目前只停"生成"，**场上已有单位仍会继续互相攻击**。补齐需要"冻结战场"能力（遍历所有 `EntityBase` 停用 `EntityAIController`/`MovementComponent`，并考虑如何恢复）。未顺手用 `FindObjectsOfType` 实现的原因：那是一次全场景扫描，且"是否允许玩家继续操作英雄、如何重开"都未定；正确做法是先引入统一的单位注册表。

## 修复 Unity 编译错误 CS1622（14:0x）

### 报错
`Assets/Scripts/Gameplay/MatchController.cs(115,17): error CS1622: Cannot return a value from an iterator.`
指向 `StartMatchAfterDelay()`（迭代器）里的 `return;`。

### 根因
**迭代器块（方法体内含 `yield return` / `yield break`）里不允许出现普通 `return;`，结束迭代只能写 `yield break;`。**
写协程时按普通 void 方法的习惯顺手写了 `return;`，于是编译失败。
修复：`return;` → `yield break;`，并在注释里写明"为什么不能写 return"。

全项目排查：仅 3 个迭代器方法（`MatchController.StartMatchAfterDelay` / `MinionSpawner.SpawnLoop` / `Stage2AutoTester.RunTestRoutine`），
另两个本来就用 `yield break` 或没有 return，**只有这一处**。

### 顺带加固：`check_unity_cs.py` 新增第 6 项检查
这次的教训是**工具盲区**：前五项（BOM/括号/命名空间/双引号/危险命名空间）全部通过，编译器却直接失败。
所以新增「迭代器内的裸 return」检查：
- 用正则锚定 `IEnumerator` / `IEnumerable[<T>]` + 方法名 + 参数列表 + `{`，再花括号配对定位方法体，搜 `return\s*;`。
- 变量声明（`IEnumerator foo = Bar();`）因中间隔着 `=` 不会被误匹配。
- 新增自测脚本 `.workbuddy-ai/tools/test_check_unity_cs.py`（6 用例，全通过）。
  **最关键的是第 3 个用例**：同一文件里既有迭代器、又有含 `return;` 的普通 void 方法，必须不报错 ——
  这正是最初"文件级粗粒度判断"会踩的假阳性（`MatchController` 本身就有这种结构）。

### 现状
`check_unity_cs.py` = 六项检查；30 个 `.cs` 全部通过；仍需 Unity 内确认编译通过。
