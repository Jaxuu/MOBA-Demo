## 09-26 阶段八白盒视觉反馈补丁（架构师指令：血条 Bug + 小兵阵营色 + 占位特效）

### 1. 英雄无血条：真因是「满血隐藏」+「池拒绝不可恢复」两条，不是注册顺序
- **取证**：`MainScene.scene` 里血条模板 `hideWhenFull: 1`；README 对血条的要求只有「跟随头顶 / 敌我配色 / billboard / 池化复用」，**没有**"满血隐藏"这一条（旧代码注释里的"README 明确要求"是写错的）。英雄死亡后 `HealthComponent.Revive` 把生命填满 → 满血 → 血条整条被禁用，观感就是"英雄压根没挂血条"；小兵长期带伤所以看起来"只有小兵有血条"。
- **第二条静默失效**：`PrefabPool` 是硬上限，`Get()` 返回 null 时 `HandleEntityRegistered` 直接 return，而登记事件**只广播一次** → 被拒绝的单位**永久**没有血条（池腾出的位置只被后续新登记的单位用掉）。Editor.log 里 `[PrefabPool] HealthBarTemplate 的池已耗尽（容量 48）`（栈来自 `MinionSpawner.SpawnOne → EntityBase.OnEnable`）证明确实发生过。
- **修法**：① `hideWhenFull` 默认改 false，并由工具在 `BuildHealthBars` 里 `AssignBool(view, "hideWhenFull", false)` **显式写入**（模板是已存在资产，改 C# 默认值对它无效 —— 与 `PatchMinionPrefabTuning` 同源的坑）；② 引入三层挂载保障：事件订阅（原有）→ **首帧末全量 `Snapshot()` 补挂**（覆盖"订阅晚于登记"的窗口）→ **可恢复原因（池耗尽 / 相机未就绪）的补挂队列 + 0.5s 定时重试**；三条都走同一个 `TryBind` 入口。③ 补挂结果打一条汇总日志（`血条就绪：当前显示 N 条…`）—— 让"补挂跑了但无需补挂"与"压根没跑"在 Console 上可区分。

### 2. 小兵阵营配色（新增 `Scripts/VFX/TeamColorView.cs`）

### 3. 白盒占位特效（新增 `Scripts/VFX/WhiteboxVfxManager.cs` + 3 个配套）
- **事件名纠正**：`SkillComponent` 没有 `OnSpellCast`，只有 `OnCastStarted`（校验通过、扣蓝起 CD 后）与 `OnSpellReleased`（真的生成了效果载体后）。管理器订阅 **`OnSpellReleased`** —— 语义正好是"效果已落地"，且不会出现"没打出去却播了特效"。

## 09-26 首轮组装报错修复（3 项，其中 1 项是本轮引入的、2 项是查错时顺带挖出的真 Bug）

### 报错 1（本轮引入）：`NameToLayer is not allowed to be called from a MonoBehaviour constructor (or instance field initializer)`
- 写法 `private static readonly int IgnoreRaycastLayer = ResolveIgnoreRaycastLayer();` —— 静态字段初始化器在**类型加载**时执行，Unity 禁止在其中调 `LayerMask.NameToLayer`，异常升级为 `TypeInitializationException`，**连 `Undo.AddComponent<WhiteboxVfxManager>` 一起失败** → `VfxRoot` 上压根没挂上管理器（特效整块静默失效，但组装仍"成功"）。
- 修法：改成**实例字段 + 在 `Awake` 里解析**（默认值直接写引擎内置约定值 2；编辑器里 `AddComponent` 不跑 Awake，此时默认值依然是正确的）。**通用教训：MonoBehaviour 的字段初始化器里只能放纯常量 / `new`，任何引擎查询（NameToLayer / Shader.Find / GetComponent）都必须挪到 Awake。**
- 取证旁证：`CompileScripts` 在组装之前有一次 6200ms 的完整编译且**其后再无 `error CS`** → 新文件本身编译是过的，这条是编辑器期异常而非编译错误。

### 报错 2（上一轮遗留）：`在 MatchDebugView 上找不到序列化字段「matchController」`
- `BuildDebugViews` 里写着 `AssignObjectReference(matchView, "matchController", matchController)`，而 `MatchDebugView` **从未声明过该字段**（它读静态事件 `BaseCoreController.OnBaseDestroyed` + 静态方法 `MatchController.GetOpponentTeam`，自己 `FindObjectsOfType` 找基地）→ 每次组装必刷一条红色假错误。**这类假错误比没有校验更糟：它会训练人忽略 Console。**
- 修法：删掉这次注入，并把 `BuildDebugViews` 的 `matchController` 参数一并去掉（不留"看着像要用"的死参数），调用点同步更新。

### 真 Bug 3（查错时挖出，最严重）：E 审判退化成"对自己造成 18 点伤害"
- **链路**：`SkillData.OnValidate` 里有一段「`castType == Self && !spawnZoneAtSelf` → 把 `areaDuration/tickInterval/effectRadius/followCaster` 就地清零」的归一化。`OnValidate` 会在**脚本加载时**对每个已加载资产各跑一次，而 `spawnZoneAtSelf` 是后加字段、旧资产序列化数据里根本没有它 → 反序列化必然是 false → **每次加载都顺手把 `followCaster` 清成 false**。
- 而 `EnsureSelfZoneFlag` 的判据恰好是「`followCaster == true` 且 `spawnZoneAtSelf == false`」→ **旁证被抹掉后判据永远不成立，自愈一次都没跑过**（日志里那句 `followCaster = False / spawnZoneAtSelf = False，无需补写` 就是现场证据）。
- 后果：E 的 `spawnZoneAtSelf` 始终为 false → `SkillComponent.Release()` 走"把主效果作用于自身"分支 → 按 E **自己掉 18 点血**，且 Console 全静音。（顺带解释了为什么 Q/W 的 `areaDuration` 在磁盘上是 4、工具却报"均为 0，无需归一化"—— 读的是被 OnValidate 改过的内存副本。）
- 修法两条：
  1. **`SkillData.OnValidate` 删掉那段跨字段归一化**（只保留"单独看就非法"的夹取：半径 0 兜 1）。归一化改由工具在组装时显式做（`NormalizeSelfSkillRangeFields`，带日志可复核）。**通用教训：`OnValidate` 会因为"新字段尚未序列化"而误判，因此它只能修正单字段非法值，不能基于跨字段推断改写别的字段。**
  2. **`EnsureSelfZoneFlag` 判据改成显式身份**（本方法只服务 E 资产，E 的定义就是"以自身为中心、跟随自己的持续 AOE"，只要开关是假的就补）—— 不再依赖任何会被别处改写的旁证；并顺手按设计常量修复被清零的范围值（否则补完开关后的 `SaveAssets` 会把内存里的 0 落盘，把设计值彻底毁掉）。

## 第四轮修复（架构师实机打回）：两个「静默失效」的根因

> 打回症状：① 红方小兵不是黑色（双方小兵同色）；② 9 个 AI 依然全在放玩家的盖伦 QWER（转大风车 / 劈大宝剑），而工具的收尾校验却说「技能全部来自技能池」。

### 取证方法（值得复用）
- **先看「上次组装」与「上次编译」的先后**：`grep -n "测试战场组装完成\|CompileScripts" Editor.log | tail`。
  本次证据：最后一次组装在 251735 行、最后一次编译在 276857 行 → **改完代码后根本没重跑过组装菜单**，场景/预制体仍是上一版代码的产物。
- **直接读落盘资产的 YAML**，不要读代码里的意图：`grep -n "allyMaterial\|allyHeroMaterial" Assets/Prefabs/MinionPrefab.prefab`。
- **把「模板侧」与「实例侧」的值都抓出来**：`HeroStats.asset` 的 `skillQ..skillR` 指向盖伦四件套；场景 YAML 里 AI 实例的 `skillSlots[2]/[3]` 是 `{fileID: 0}`。

### 根因 ①：改序列化字段名 = 一次静默数据迁移
- `TeamColorView` 的字段从 `allyMaterial/enemyMaterial/neutralMaterial` 改成四格表后，`MinionPrefab.prefab` 里存的**仍是旧字段名**；C# 侧字段已删除 → Unity 反序列化时**静默丢弃**旧值 → 四个新字段全 null → `ResolveMaterial` 返回 null → "保持原材质" → 双方小兵同色。
- 而这条分支当时只有 `logApply = false` 的可选日志 → **整件事一点声音都没有**。
- 修法：小兵配色注入**前移到步骤 15**（与英雄同批）+ 步骤 16 新增 `ValidateEntityColorInjection` 读回两个预制体的四个字段（存在/非空/等于本次材质）+ `PatchPrefabTeamColor` 把「字段不存在」与「值已正确」区分开（前者返回 false 并报错）+ `TeamColorView` 在英雄/小兵拿不到材质时**报一次 LogError**（静态标记防刷屏）。

### 根因 ②：运行期存在第二个写入者（这才是「假写入」的真相）
- `EntityBase.ApplyStats`（Start）拿**共享**的 `EntityStatsData` 调 `SkillComponent.Initialize`；上一版 `Initialize` 是"传进来的非 null 就写" → 10 个英雄共用同一份 `HeroStats`（配着盖伦四件套）→ 9 个 AI 实例上按技能池注入的 `skillSlots` **在 Start 时被整体改写**。
- **编辑期注入是真的、场景里看 Inspector 也是对的**，覆盖只发生在 Start 之后 → 工具侧任何「读回序列化字段」的校验都查不出来（上一轮我加的 `ValidateAiSkillAssignment` 就是这样被绕过的）。
- 修法三层一起断链：
  1. **数据层**：组装时**清空** `EntityStatsData` 的四个技能字段（`ClearHeroStatsSkillFields`，带说明日志）→ 运行期这条链拿到 4 个 null；
  2. **代码层**：`SkillComponent.Initialize` 改为「**实例整体接管，模板只服务全新单位**」——任意一槽非空即整体跳过模板（**不能用「只补空」**：那会给 AI 的空槽补上玩家技能），且"模板被忽略"时报一次警告；
  3. **证据层**：`HeroAIController` 在 Start 时把最终生效的四个技能打进 Console（9 行运行期证据），空槽位用 Warning 点名。

### 通用教训（写进 MEMORY）
- **「写进去了」≠「生效了」**：只要某个字段在运行期还会被写一次，编辑器侧的读回校验就只能证明"磁盘上写了什么"。这类字段要么收敛成一个写入者，要么把优先级写成显式规则 + 运行期留一条自证日志。
- **改序列化字段名必须配套读回校验**：Unity 对已删除字段的值是**静默丢弃**，症状是"看起来没生效"而 Console 安静。
- **删除 partial 类里的方法前必须全仓 grep**：本轮我删掉 `PatchObjectReferenceIfUnset` 时漏看它仍被 `Stage8Assembly`（塔攻击资产）与 `UIAssembly`（技能图标）调用 —— 差点制造一个 CS0103。**partial class 的"私有方法"其实是跨文件的公共工具，删之前先 `grep -rn` 全 Editor 目录。**
- **静默降级要分级**：表现层"没配置就保持原样"是合理降级，但「英雄 / 小兵没有阵营色」是装配缺陷 → 必须 LogError。
- 场景/预制体的组装产物**必须重跑一次菜单**才会更新：本轮两个问题都要求重跑（配色注入、AI 四槽写入）。

### 关键决策（踩坑预防）
- **`AnimationComponent` 不聚合到 `EntityBase`**：它自己解析依赖，加一个没人读的 `EntityBase.Animation` 就是死代码，还会诱导逻辑层经它碰表现。Plan 的类图同步删掉了 `EntityBase *-- AnimationComponent`（与 `TeamColorView` 同一先例）。

- **控制器过渡的幂等策略 = "已存在一律沿用"**（只加不减不改）：过渡时长是美术会调的参数，每次组装都写一遍等于把人的调整打回去。
- **`AnimatorController.CreateAnimatorControllerAtPath` 生成的控制器 `defaultState` 为 null** → 必须显式设成 Idle，否则运行期"单位一动不动"且不报错。

- **空状态（无片段）的退出时间过渡行为由引擎决定，本阶段不做断言**：画面上本来就什么都看不到，这条过渡是为挂上片段之后准备的（注释里写明）。

### 资产获取：两条逆向路线（都可复用）
1. **盖伦模型**：`tengge1/lol-model-viewer` 仓库自带 `.lmesh`（作者私有格式，仓库里**没有转换器源码**）
   → 读 `viewer.js` 的 `loadMesh`/`Lol.Vertex` 得到定义 → 写 `.workbuddy-ai/tools/lmesh2obj.py`。
   格式：`magic 604210091` + u32 version + 两个 u16 长度前缀字符串 + 网格表 + 顶点(52B) + 索引(u16)。
2. **小兵模型**：CommunityDragon **镜像了 `.skn`**（`game/assets/characters/sru_orderminionmelee/skins/base/`），
   还自带**蓝/红两份贴图**。`.skn` 是 LoL 原生格式、无现成 Python 解析器 → **字节级实测反解**
   → `.workbuddy-ai/tools/skn2obj.py`：
   ```
   0x00 magic 0x00112233 | 0x04 u16 major,minor | 0x08 u32 objectCount(=1)
   0x0C char name[64] | 0x50 vertexCount | 0x58 indexCount | 0x68 vertexSize(=52)
   0x98 u16[indexCount]   ← 索引块
   紧随其后 52B × vertexCount 顶点块，末尾 12B 尾记录
   顶点: position@0 / boneIndices(u8×4)@12 / weights(f32×4)@16 / normal@32 / uv@44
   ```
   **三条交叉判据（必须同时成立才算解对）**：① 索引零越界；② 全部法线为单位向量；③ 块边界 == 文件长度。
   判别技巧：同一份数据用两种布局假设分别解析，**越界索引为 0 的那个才是对的**（本次 0x98 vs 0xA4 就是这样定案的）。

### `.skn` 多对象格式破解（本轮最大技术难点）
上一轮解析器只支持 `objectCount == 1`。塔是 8 对象、水晶 2 对象。实测反解出完整布局：
```
0x00 u32 magic | 0x04 u16 major,minor | 0x08 u32 objectCount
每对象 80 字节：char name[64] | u32 vertexStart | u32 vertexCount | u32 indexStart | u32 indexCount
60 字节尾部：u32 ? | u32 totalIndexCount | u32 totalVertexCount | u32 vertexSize | u32 ? | f32[10]
数据块：u16[totalIndexCount] 索引块 → u8[vertexSize × totalVertexCount] 顶点块 → 12 字节尾
```
**四条交叉判据**（脚本内置，任一不满足就报错退出）：① 长度方程精确闭合；② 索引零越界；
③ 单位法线比例 ≥ 99%（turret 有 7/22849 个源数据退化法线 → 修补为 (0,1,0)，阈值放宽到 99% 仍能抓错位）；
④ 每对象的 start 与前面对象计数累加严格吻合。
工具还按语义**自动剔除残骸变体**（名字含 rubble/broken/destroyed）—— 塔的 8 个对象里 Base/Stage1-3 是完整的塔，Rubble/Broken1-3 是废墟，叠在一起会重影。

### 实机踩出来的三个真问题（都已修）
1. **玩家英雄没模型**（9 个 AI 都有，唯独主角没有）→ 根因：`CreateHeroInstance` 对玩家英雄有一处**提前 `return`**，

### 自动化实测的环境坑：`PlayerSettings.runInBackground`

编辑器一失焦播放循环就被节流到近乎停止。**这会让"自动进 Play 跑 1 分钟"变成一句空话（跑的是墙钟时间，不是游戏时间）。**
